        SDD001
        OTP supervision tree for one airport group
        The Tower CSCI shall start under an OTP application and a one-for-one supervisor. The supervisor shall own the configuration loader, the local log, the neighbor monitor, and the clearance service. A child crash shall restart that child without creating a second log. Acceptance is an application start that registers one supervisor, and a killed child that is restarted while the committed log prefix is unchanged.
        Supervision is how a local computer returns a worker without inventing a new authority.

        SDD002
        Clearance state machine and the TLA+ actions that match it
        The clearance state machine shall use the phases out, queued, hold, occupying, and air. The actions shall be assign, sequence, hold short, line up and wait, takeoff, land, go-around, and handoff, and each action shall match a TLA+ action of the same name in AtcTower. Occupying means the aircraft is inside the protected volume. Acceptance is a review that every Erlang action name appears in the TLA+ spec and that a sampled transition produces the same phase change in both descriptions.
        The design keeps one action vocabulary so the refinement mapping has something to point at.
        A
        Low-Level
        Refinement
        The checked envelope is 4 runways, 8 aircraft under control, and 2 neighbor airports. Visual separation, LAHSO, radar vectoring, TRACON, enroute control, and wake RECAT are outside this increment.

        SDD003
        Refinement mapping from Erlang state to TLA+ state, including open obligations
        The design shall include a refinement mapping from the Erlang clearance state to the TLA+ variables for phase, runway, sequence, and link status. The mapping shall list the Raft ordered-log assumption and every obligation that TLC and PropEr do not discharge, and those obligations shall remain labeled open. Acceptance is a mapping document linked from this requirement that a reader can use to find each Erlang field in the spec, and that does not describe an open obligation as proved.
        The mapping is derived design evidence. It is not a completed machine-checked refinement proof.
        A
        Derived
        Refinement
        Raft is assumed to deliver one ordered log and is not re-proved. Open obligations stay open until a later proof discharges them.

        SDD004
        Consensus assumption: the Raft log is a single ordered history and Raft is not re-proved
        The local group shall use Ra as the Raft log. The design shall treat a committed Ra index as the single ordered history and shall not include a proof of Raft. Commands shall be submitted only by the current Ra leader. Acceptance is a three-member Ra cluster in one Erlang node that commits one clearance and rejects a command from a follower that is not the leader.
        Re-proving Raft is out of scope. Using a known library keeps the assumption explicit.

        SDD005
        Fail-smart mode and the stale-neighbor rule
        Neighbor state shall be a record with a link flag and a stale flag. When the link is down the stale flag shall be set and the handoff action shall be disabled. Local clearance actions shall ignore stale neighbor occupancy when deciding whether a local volume is free. Acceptance is a neighbor record that becomes stale on link loss and a local landing that is still decided only from local occupancy.
        Stale data remains visible for the operator and unusable for reducing separation.
