    1. SDP001 Lifecycle, Wikipedia DID set, tailoring, DAL, Erlang, TLA+, and trace rules
    SDP001
    1.1. Lifecycle, Wikipedia DID set, tailoring, DAL, Erlang, TLA+, and trace rules SDP001 The software development plan shall follow DO-178C objectives for the Tower CSCI and shall record lifecycle data with the MIL-STD-498 data item descriptions: Software development plan (SDP), Software installation plan (SIP), Software transition plan (STrP), Operational concept description (OCD), System/subsystem specification (SSS), Software requirements specification (SRS), Interface requirements specification (IRS), System/subsystem design description (SSDD), Software design description (SDD), Database design description (DBDD), Interface design description (IDD), Software test plan (STP), Software test description (STD), Software test report (STR), Software user manual (SUM), Software input/output manual (SIOM), Software center operator manual (SCOM), Computer operation manual (COM), Computer programming manual (CPM), Firmware support manual (FSM), Software product specification (SPS), and Software version description (SVD). SSS is the system specification and SRS is the software specification. Separation, an unsafe clearance, and fail-smart behavior are DAL A. The implementation language is Erlang and the formal model is TLA+. Each requirement fragment names its parents, and each implementing source file names the requirement UID in a comment and in the commit that adds it. This repository records that evidence and does not claim certification authority approval.
    • SDP002
      2.1. SIOM, SCOM, COM, CPM, and FSM tailored out, with reasons SDP002 The project shall tailor out the Software input/output manual (SIOM), the Software center operator manual (SCOM), the Computer operation manual (COM), the Computer programming manual (CPM), and the Firmware support manual (FSM). SIOM and SCOM describe a batch or interactive system installed in a computer center, and this tower is not that system. COM and CPM describe operating and programming a general-purpose computer, which is outside the Tower CSCI. FSM describes firmware devices, and this CSCI has no firmware. Acceptance is this requirement stating those five acronyms and the reason each is absent, with the delivered set limited to the remaining descriptions.
    • SIP001
      1. Install one release on n airport computers and point them at the TOML file SIP001 Installation shall place the same Tower release on each of the n computers for one airport and shall point every computer at that airport TOML file. The installer shall not start control until the file passes the configuration check. Acceptance is a procedure a support engineer can follow for n equal to 1 and for n equal to 3, with a bad file leaving the computers stopped.
    • SPS001
      1. Delivered tower sources, model, and requirements SPS001 The product specification shall list the Tower CSCI artifacts delivered in this version: the Erlang modules and tests under apps/atc_tower, the example airport file config/example-airport.toml, the TLA+ specification specs/tla/AtcTower.tla with specs/tla/AtcTower.cfg, the refinement mapping specs/refinement/Mapping.md, and the StrictDoc sources under reqs. The mapping's open obligations remain open. Acceptance is a reader finding each of those paths in the version that this specification describes.
    • SRS016
      1. Record each decision with the requirement UID it carried out SRS016 The Tower CSCI shall append an audit record for every issued clearance and every refusal. The record shall contain the aircraft identity, the clearance kind, the runway when one was named, the decision, and the requirement UID of the software requirement that authorized that kind of decision. Acceptance is a landing grant whose audit line contains SRS011, and a refusal whose audit line contains the UID of the guard requirement SRS013.
      • DBDD001
        1.1. The replicated clearance log is the operational store and TOML is configuration read at startup DBDD001 The operational store shall be the replicated clearance log, not a separate database. Each committed entry shall hold the command, the resulting decision, and the requirement UID recorded in the audit. The TOML file shall be read at startup and shall not be written by the clearance path. Acceptance is a committed landing whose log entry contains the aircraft and SRS011, and a running node that does not modify the TOML file.
      • STD012
        1. Audit trace contains the requirement UID STD012 The test shall issue a landing and refuse an unsafe line-up, then read the audit. The landing record shall contain SRS011 and the refusal shall contain SRS013, along with the aircraft identity and the decision. Acceptance is both records present and no issued record for the refused line-up.
    • STP001
      1. Which SRS items are discharged by TLC, by refinement review, by PropEr, and by example tests STP001 The test plan shall discharge SRS013 and SSS007 by TLC on AtcTower, SRS013 and SSS008 by review of the refinement mapping, SRS004 and SRS015 by PropEr state-machine tests, and the remaining software requirements by Common Test examples named in the software test description. A PropEr failure shall fail the build and shall not be rewritten as formal proof. Acceptance is a trace from each SRS item to one of those four methods, and a test run whose failing property stops the suite.
      • STD001
        1. TOML accept and reject cases STD001 The test shall load the example airport TOML and expect a parsed airport with its runways, then load an empty file and a runway without a designation and expect both to be rejected before any clearance is issued. Acceptance is those three results, with the valid file producing a runway list and the two invalid files producing an error and no authority.
      • STD002
        1. Runway designation selection cases STD002 The test shall attempt a landing on a departure-only runway, a takeoff on an arrival-only runway, an assignment to a closed runway, and a dual occupancy of two non-independent runways. Each attempt shall be refused. A landing on an empty both-use runway shall be accepted. Acceptance is those five outcomes.
      • STD003
        1. Group membership for one computer and for three STD003 The test shall start a group with n equal to 1 and expect that member to be the authority, then start a group with n equal to 3 and expect a member that has not joined to refuse a clearance. Acceptance is authority on the single member and refusal from the unjoined member.
      • STD004
        1. One clearance authority under a crash STD004 The test shall start three log members, commit one clearance, stop one member, and expect the surviving majority to accept one further clearance while the stopped member accepts none. It shall also partition the three into a side of one and a side of two and expect only the side of two to accept a clearance. Acceptance is one committed clearance after the crash and a refusal from the minority side.
      • STD005
        1. Neighbor distance selection STD005 The test shall place one candidate inside the communications distance and one outside it and expect only the inside candidate to be selected as a neighbor. Acceptance is a neighbor set of size one containing the inside airport.
      • STD006
        1. Handoff while the neighbor link is up STD006 The test shall send a handoff to a neighbor whose link is up, accept it, and expect the aircraft to leave local control. A second handoff that the neighbor rejects shall leave the aircraft in local control. Acceptance is those two outcomes.
      • STD007
        1. Partition fail-smart case STD007 The test shall bring a neighbor link down, mark the neighbor picture stale, grant a local landing that the local guard allows, and refuse a handoff. It shall also show that the stale picture is not used to permit a second aircraft into a locally occupied volume. Acceptance is the granted local landing, the refused handoff, and the refused double occupancy.
      • STD008
        1. Queue, landing, takeoff, and runway assignment path STD008 The test shall assign a both-use runway, sequence two aircraft, hold the second short, line the first up, clear the first for takeoff, and then clear the second to land only after the first is airborne. A landing attempted while the first still occupies the runway shall be refused. Acceptance is that ordered path and the one refusal.
      • STD009
        1. The guard refuses an unsafe clearance STD009 The test shall submit a line-up for a second aircraft while the first occupies the runway and expect a refusal with the state unchanged. It shall then go around or complete the takeoff and expect the second line-up to be accepted. Acceptance is the refusal with an unchanged log prefix and the later acceptance.
      • STD010
        1. PropEr state machine for concurrency, crash, recovery, and agreement STD010 The PropEr state machine shall generate sequences of clearance commands, concurrent submissions, a member crash, and a restart that replays the log. Every accepted sequence shall preserve the exclusive-volume invariant, and every crashed member that restarts shall match the surviving log prefix before it accepts a new command. A failing property shall fail the build. Acceptance is a PropEr run of this module that passes, and a deliberate invariant break that fails the property.
      • STD011
        1. Bounds refusal STD011 The test shall reject a configuration with 5 runways, reject a configuration that allows more than 8 aircraft, and reject the ninth aircraft at an airport already holding 8. Acceptance is those three refusals and no issued clearance in the first two cases.
      • STD012
        1. Audit trace contains the requirement UID STD012 The test shall issue a landing and refuse an unsafe line-up, then read the audit. The landing record shall contain SRS011 and the refusal shall contain SRS013, along with the aircraft identity and the decision. Acceptance is both records present and no issued record for the refused line-up.
      • STR001
        1. Record of the TLC run and the Common Test run STR001 The test report shall record the commands that were actually run and the results they printed. On 2026-11-20, from the repository root, rebar3 as test ct reported All 15 tests passed, covering atc_config_SUITE, atc_clearance_SUITE, and atc_cluster_SUITE, and the last of those calls prop_clearance:quickcheck/0 with 40 cases. make tla-check reported no error on AtcTower, with 414 distinct states and depth 8. make run printed airport KEXAMPLE ready on 1 computers. The PropEr result is conformance evidence and is not a proof. Acceptance is this record matching those commands and results.
    • STrP001
      1. Hand the release, the TOML, the model, and the open proof obligations to a support engineer STrP001 Transition to support shall hand over the release, the airport TOML file, the TLA+ model and its TLC result, the refinement mapping, and the list of open proof obligations. Support shall not be told that PropEr or TLC discharged an obligation the mapping still marks open. Acceptance is a handover list that contains those items and that repeats each open obligation in the same words as the mapping.
    • SUM001
      1. Start, stop, and edit runway designations for one airport SUM001 The operator manual shall tell an operator how to edit runway designations in the airport TOML file, start the n local computers, and stop them. It shall state that a closed runway will not be assigned and that a file outside the checked envelope will not start. Acceptance is a manual section that names the TOML keys for designation and the start and stop commands, and an operator who can close a runway by editing the file and restarting.
    • SVD001
      1. Version 0.1.0 of the tower CSCI SVD001 The version description shall identify atc_tower 0.1.0, dated 2026-11-20, as the rebar3 release of the Tower CSCI together with AtcTower.tla, the refinement mapping, the StrictDoc sources, and the HTML generated under reqs/html. It shall record the TLC result of 414 distinct states with no invariant error and the Common Test result of 15 passing tests. Acceptance is a version record that names those artifacts and results and does not claim certification authority approval.
